# esp_system

Бэкенд умного дома (FastAPI + Redis + MQTT + self-hosted S3 на Garage) для платы
ESP8266/ESP32: телеметрия, погода, видеонаблюдение с камер и распознавание лиц
через отдельный `recognition_worker`. Веб-интерфейс — `esp_front`.

## Эксплуатация

### Инцидент: деградация garage/mosquitto из-за OOM-килов esp_service (авг 2026)

**Симптом.** На сервере переставало отвечать S3-хранилище (`garage`), позже то же
самое началось и у MQTT-брокера (`mosquitto`) — оба контейнера уходили в
`unhealthy`, `docker exec` внутрь них падал с `procReady not received`.

**Ход расследования (кратко).**
- Оба контейнера упирались в потолок `pids.max` cgroup (~2129 задач) — новый
  процесс внутри создать было уже нельзя, поэтому и healthcheck, и `exec`
  переставали работать.
- Первая находка: `esp_service` не закрывал соединение к S3 при обрыве клиента
  (перемотка видео в плеере обрывает текущий Range-запрос) — генератор в
  `s3_manager.py` не читал тело ответа до конца и не закрывал его явно.
  Пофикшено (`try/finally` с `body.close()` в `get_video_stream` и
  `stream_range`), но проблема вернулась и на второй, не связанный с S3
  контейнер (`mosquitto`) — значит, это была не единственная причина.
- Настоящая первопричина: `esp_service` (`mem_limit: 200m`) регулярно убивался
  ядерным OOM-killer'ом (cgroup-лимит памяти) — 5 раз за 48 часов, видно по
  `journalctl -k | grep -i oom`. Один раз ядро устроило уже **глобальный** OOM
  всего хоста и убило `recognition_worker`. Внезапный `SIGKILL` не даёт
  процессу закрыть соединения к S3/MQTT корректно — отсюда и накопление
  "подвисших" ресурсов на стороне `garage`/`mosquitto` при каждом падении.
- Хост — VPS на 1.8GB RAM без swap; сумма `mem_limit` по всем контейнерам в
  `docker-compose.yml` уже превышала физическую RAM ещё до этого инцидента.

**Что сделали.**
1. Добавили 2GB swap-файл (`/swapfile`, `vm.swappiness=10`), закреплено в
   `/etc/fstab` — переживает перезагрузку сервера.
2. `esp_service`: `mem_limit` `200m → 384m`, `mem_reservation` `100m → 150m`
   (сборка видео от камеры идёт в памяти + параллельно `ffmpeg`, 200MB было
   объективно мало).
3. `garage`: добавили `mem_limit: 512m` — раньше был единственным сервисом в
   compose вообще без лимита памяти.
4. Временно отключили второй CV-проход в `recognition_worker` — определение
   направления вход/вышел (`door_direction`, v7). Он гонял ещё один полный
   YOLO-инференс на каждом кадре видео поверх основного распознавания лиц,
   заметно нагружая и без того тесную по RAM/CPU машину, и был отмечен
   в коде как сырой. Код **не удалён** — закомментирован в
   `recognition_worker/worker.py` (импорт, вызов, часть print'а). Возврат —
   раскомментировать эти 3 места. `esp_service`/фронт уже штатно
   обрабатывают отсутствие `direction` в результате как "ещё не обработано"
   (правок с их стороны не потребовалось).

**Не проверено на момент записи.** Не подтверждено по `journalctl -k`, что
OOM-килы прекратились или стали реже после пп. 1-3 — требуется понаблюдать
хотя бы сутки-двое после деплоя.

### Юзеры: миграция с хардкода на Redis-сущности (авг 2026)

Раньше юзер был просто Telegram ID, имена и админ-роль были захардкожены в двух
местах (`USER_NAMES`, `ADMIN_USER_ID`). С добавлением группового чата (см.
`docs/CHAT_TODO.md`) юзеры стали сущностями в Redis — `user:{id}` hash +
`users:index` set, сидируются идемпотентно при старте из
`CacheManager.SEED_USERS` (`esp_service/app/services/redis/cache_manager.py`).

**Аудит миграции (2026-08-24).** Прошлись grep'ом по всему репо на предмет
старых ссылок (`USER_NAMES`, `ADMIN_USER_ID`, хардкод ID юзеров) — не осталось
нигде. Всё, что раньше опиралось на старую модель (статистика визитов,
`login_stats`, `/auth/me`), переведено на `cache.get_user()` / `is_admin()` и
деградирует аккуратно: если юзера в Redis нет — фолбэк на `f"ID {uid}"` /
`str(user_id)` вместо падения.

**Найдено и поправлено:**
- В `SEED_USERS` `username` для Лилии был `lilia`, а реальная папка датасета
  лиц — `recognition_worker/dataset/liliya`. Один и тот же человек, просто
  разное написание в двух независимых системах (auth username vs CV-метка
  распознавания). Поправлено на `liliya` — единообразно с датасетом
  (переименовывать сам датасет не стали, там уже обучен `classifier_v2`).
  Если чат уже разворачивали на проде — `seed_users_if_missing()`
  идемпотентный и не тронет существующую запись, нужно поправить руками:
  `HSET user:4382099 username liliya`.

**Найдено, чинится следующим шагом:**
- `POST /auth/generate_key` (`esp_service/app/api/endpoints/auth.py`) изначально
  делался под Telegram-бота — принимал произвольный `user_id` по curl с
  `BOT_SECRET`, без проверки что юзер вообще существует (промах в ID тихо
  создавал рабочую сессию "юзера-призрака": `display_name: null`, сообщения в
  чате подписаны как `str(user_id)`, в `read_states` такой юзер не попадает).
  Бота больше нет, выдача ключей теперь ручная — решили убрать HTTP-эндпоинт и
  `BOT_SECRET` целиком, а вместо них сделать CLI-скрипт
  `esp_service/manage_users.py`, запускаемый прямо на сервере
  (`docker exec -it esp_service python manage_users.py <command>`):
  - `list` — все юзеры (id/username/display_name/role)
  - `key <user_id>` — отозвать старые ключи юзера и выпустить новый
  - `add <user_id> <username> <display_name> [--admin]` — новый юзер + сразу ключ
  - `remove <user_id>` — отозвать ключи и удалить юзера

  Статус: план согласован, реализация ещё не сделана — следующий шаг.

### Хранилище видео (S3 / Garage)

Self-hosted S3-совместимое хранилище [Garage](https://garagehq.deuxfleurs.fr/)
поднимается сервисом `garage` в `docker-compose.yml` (сборка — `Dockerfile.garage`,
конфиг — `garage.toml`, первичная настройка bucket/ключей — `entrypoint.sh`).
К нему обращаются `esp_service` (`app/services/s3_service/s3_manager.py`,
асинхронно через `aiobotocore`) и `recognition_worker` (`worker.py`,
`backfill_queue.py`, синхронно через `boto3`).
